# HyperCore Draft API Design Decisions

This document records implementation-oriented decisions behind `docs/hypercore/`. They are proposed contracts, not claims about a deployed interface.

| Decision | Alternatives considered | Reasoning | Source material | Compatibility implications | Engineering questions | Status |
| --- | --- | --- | --- | --- | --- | --- |
| Purpose-built streams | One broad trades/orders topic with filters | Common builder, user, liquidation, and book workflows should be discoverable without clients reconstructing semantic cuts. | Vetted P0-P2 stream priorities and customer notes | New event producers and authorization rules per stream; a broad stream can be added later as a convenience. | Can source tagging support each cut reliably? | Draft contract |
| JSON-RPC WebSocket envelope | Native-style ad hoc subscribe messages; custom non-RPC envelope | JSON-RPC correlates subscribe and unsubscribe results, carries structured errors, and has a clear notification form. | Assignment default design and common Alchemy API ergonomics | A gateway must translate or originate JSON-RPC envelopes consistently. | Handshake authentication, error codes, control-message behavior, and batching? | Draft contract |
| Opaque cursor and replay model | Timestamp-only replay; block-height-only replay | Cursors provide a durable per-subscription checkpoint while block height remains useful for backfill and audit. | Current build maps' replay objective and recovery requirements | Cursor retention must be explicit. Domain-id dedupe remains supplemental. | Cursor encoding, retention, scope, and gap behavior? | Draft contract |
| Snapshot and delta handling | Deltas only; full snapshots only | L2/L4 consumers need a known base plus ordered deltas. `l2Book` supplies snapshots and `l2BookDiff` supplies changes. | Vetted P0 L2 and diff requirements | The stream must define snapshot marker, sequencing, and reset behavior. | Are snapshots periodic, on subscribe only, or requestable? | Draft contract |
| Canonical names | Collapse names to generic `trades`, `orders`, and `book` | Preserve purpose-built names for P0-P2 scopes. Use `l4BookUpdates`, `fundingRates`, and `userNonFundingLedgerEvents` as proposed canonical names. | Vetted priority sheet and current internal naming conflicts | Existing native aliases can be documented as compatibility notes later. | Final registry, pluralization, and aliases? | Draft contract |
| Native-compatible REST plus enriched routes | Only `/info`; only distinct REST routes | Keep a low-friction native-compatible `/info` discriminator for confirmed reads; put composites under `/v1/hypercore/<operation>` to avoid overloading native semantics. | Current build map and user requirements | Gateway supports two request styles; SDK can hide differences. | Which native methods pass through unchanged? Are enriched reads POST or GET? | Draft contract |
| JSON-RPC block and batch API | REST block routes; generic database query API | A namespaced `hl_*` API supports point lookup, bounded batch recovery, explicit partial results, and stable error semantics. | Current internal JSON-RPC method list | SDKs need block-specific types and batch-cap validation. | Endpoint location, error codes, batch execution, and finality source? | Draft contract |
| Raw versus normalized block representation | EVM-shaped transactions; a single untyped payload | Separate normalized metadata from HyperCore commands, actions, events, and fills. This preserves native concepts and permits raw payload archival without polluting convenient reads. | Current build maps' HyperCore-native schema guidance | Requires schema registry and explicit `include` behavior. | What raw formats are retained and what fields are canonical? | Draft contract |
| Historical pagination | Offset paging; timestamp-only paging | Use inclusive start, exclusive end, and opaque `nextCursor` to prevent duplicates at the same timestamp and support stable progression. | Historical-query requirements | Service must retain a stable tie-breaker and document cursor expiry. | Default range, max range, sort key, and late-data behavior? | Draft contract |
| Historical export organization | One monolithic file; warehouse first | Propose partitioned Parquet in object storage before warehouse shares, with manifests and revisions. | Current P1a/P2 capture and export plans | Dataset names and partitions become a durable public contract. | Partition hierarchy, compression, schema version, manifest, and corrections? | Draft contract |
| StreamBlocks transport | WebSocket; gRPC | Place the draft in gRPC because current product sources frame it as a block pipeline and gRPC candidate, while leaving transport as a reviewable decision. | Vetted stream priority and current gated gRPC plan | A WebSocket equivalent can be added without changing block schemas. | Is it launch scope, and where is the proto? | Confirmed scope; draft transport |
